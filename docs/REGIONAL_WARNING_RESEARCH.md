For the implemented German warning layer and its verification, see the [integration checkpoint](PROGRESS.md#german-weather-warnings). Retrieval times below are UTC on November 12 (November 11 local time).

**Existing implementation.** The current warning adapter is [NwsAlertSource](../src/main/feeds/sources.ts). [FeedId and WeatherAlert](../src/shared/types.ts) and [AppCore](../src/main/core.ts) have one NWS alert source/cache/freshness bucket, with the fixed archive scope `active-US`. No Canada/Norway warning adapter, normalizer or matching integration tests were found. Existing documentation correctly records U.S.-only warnings.

**Canada: plausible official keyless publisher.** ECCC publishes Canadian weather warnings, watches, advisories and statements through [CAP XML](https://eccc-msc.github.io/open-data/msc-data/alerts/readme_alerts-datamart_en/) and [GeoMet WMS/OGC API Features](https://eccc-msc.github.io/open-data/msc-data/alerts/readme_alerts-geomet_en/). These are weather products, not a promise of all Canadian civil emergencies. GeoMet supports filtering and pagination; a collection item is not necessarily one currently active warning.

The [CAP-CP 0.4 rules](https://www.publicsafety.gc.ca/cnt/rsrcs/pblctns/capcp-ntro-rl-st/index2-en.aspx) require Update/Cancel references to affected active messages. Preserve the sender/identifier/sent identity and language/area blocks; do not infer lifecycle from feed disappearance. ECCC's [current release note](https://collaboration.cmc.ec.gc.ca/cmc/cmos/doc/CAP/CAP-Release-Note_EN.pdf) describes additional threat-area polygons alongside zone areas, with issued/continued/ended/cancelled area states, and scheduled geography/certificate changes. A parser must distinguish these areas rather than joining every polygon into an active threat.

The [August 2026 ECCC end-use licence](https://eccc-msc.github.io/open-data/licence/readme_en/) permits commercial reuse with attribution, preserves third-party exceptions, and requires weather-alert content/intent to remain intact. Credit ECCC and link its licence. The [service usage policy](https://eccc-msc.github.io/open-data/usage-policy/readme_en/) requires meaningful User-Agent identification, prohibits no-cache headers, and calls for consultation at 86,400 requests/day or above. Real-time Datamart delivery must use AMQPS; directory availability polling is prohibited. Ad hoc retrieval is distinct from systematic ingestion. The policy recommends Datamart, not GeoMet, for building archives. Thus the existing desktop JSON-poll/archive path cannot simply be pointed at this directory or assumed suitable for production CAP history.

**Norway: documented candidate; live data not requested.** [MetAlerts 2.0 documentation](https://api.met.no/weatherapi/metalerts/2.0/documentation) describes Norwegian meteorological warnings for land, coastal and sea regions, with current RSS/CAP and a beta GeoJSON representation. Flood warnings are a separate NVE source. The documentation says CAP documents are immutable: cache each once and follow replacement IDs. GeoJSON remains described as costly/beta, so its availability is not a high-volume production guarantee.

The [MET CAP v2 profile](https://docs.api.met.no/doc/metalerts/CAP-v2-profile.html) distinguishes message identity, Update/Cancel references and bilingual info blocks. Cancellation can invalidate an incorrectly issued warning; an AllClear downgrade is an Update. Expiry limits message validity, not the time weather becomes safe. Polygons can cross borders although warning authority remains national. Do not generalize this into global or all-Nordic warning coverage.

[Licensing](https://docs.api.met.no/doc/License.html) specifies NLOD 2.0/CC BY 4.0 with MET Norway credit. The [terms revised November 5, 2026](https://api.met.no/doc/TermsOfService) require identifiable/contactable clients, cache/Expires and conditional-request discipline, immutable-CAP reuse, traffic below 20 requests/second **per application**, and no more than one poll per ten minutes for push-style MetAlerts use. They explicitly require terms to be “read, understood and accepted by a human in authority before using our service.” No such acceptance was established in this task; only documentation was reviewed, and no MetAlerts data endpoint was called. No customer account, API key or billing was activated.

**Germany DWD follow-up — November 12, 2026 UTC.** A fresh source/test search found no DWD CAP ingress. The existing saved-location evidence repair remains NWS/USGS-only. DWD is a more direct candidate for a keyless desktop snapshot than the two transport/authorization cases above, but no Atlas integration was added.

The official [Open Data README](https://opendata.dwd.de/README.txt) explicitly provides free access without registration, with IP logging for up to seven days. The current [DWD legal notice](https://www.dwd.de/EN/service/legal_notice/legal_notice_node.html), read successfully over direct HTTPS, licenses open spatial/weather information under CC BY 4.0 with source acknowledgement. Its [current attribution template](https://www.dwd.de/DE/service/rechtliche_hinweise/vorlagen_quellenangabe.html) allows excerpts/format conversion with attribution, requires alteration notices for further changes, and requires the supplied source mark to be removed if official warning content is altered. Preserve original warning text and distinguish map formatting from an altered official warning. No API key, subscription, AMQPS-only transport rule or special human-acceptance clause was found in the reviewed Open Data documents. No numerical request quota or guaranteed archive-size ceiling was established; this is not permission for unlimited polling or an SLA.

The official [CAP product overview](https://www.dwd.de/DE/leistungen/opendata/help/warnungen/dwd_warnings_products_overview_en_pdf.pdf?__blob=publicationFile&v=3) distinguishes complete `STATUS` from incremental `DIFFERENCE`. `COMMUNEUNION_DWD_STAT` supplies the national DWD warning situation using fused municipality geometry and WarnCellID references; district products are coarser, not a separate global warning service. The [processing notes v2.1.8](https://www.dwd.de/DE/leistungen/opendata/help/warnungen/cap_dwd_implementation_notes_de_pdf.pdf?__blob=publicationFile&v=5), downloaded and read locally, describe production up to once per minute, a refresh after ten unchanged minutes, DWD-specific replacement/all-clear rules, and polygon holes in `EXCLUDE_POLYGON` geocodes. STATUS supports restarting without replaying every missed difference. It does not establish every intermediate event while the client was closed.

One documentation limit matters: the 2017 processing notes say language identifiers are identical, whereas these live DE/EN samples had language suffixes `.DEU`/`.ENG`. The linked English CAP profile returned HTTP 404; no alternate profile was guessed. Several web-tool fetches returned 403, but direct official HTTPS retrieved the legal notice and processing PDF successfully. A future adapter must reconcile the current profile with observed multilingual identity before merging translations; it must not strip suffixes speculatively, draw geocode-only marine warnings as invented shapes, or treat missing expires as an all-clear. Start with one complete language/snapshot, retain source clocks and references, handle DWD holes and warn-cell geography, cache conditionally when supported, and fail visibly on size/parse/completeness limits. This establishes a credible authorized public-data path, not implemented German warning parity.
